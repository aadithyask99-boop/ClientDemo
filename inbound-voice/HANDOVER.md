### 0.6 The latency work: findings and the menu (this is the open work)
Measured "Reasoning Delay" (model time only; hearing, voice start and the phone line are extra): Dograh default model 0.8 to 1.5 s; Haiku via OpenRouter before the provider pin and prompt trims 2.3 to 3.4 s; **now typically 0.6 to 1.3 s**, with slow outliers: 3.3 s when she calls `find_appointment` THEN `check_availability` when moving a booking, 1.9 to 3.8 s on turns with a name correction, about 1.9 s closing the call. Real calls are 8 kHz and mishear names and places; text tests hide this. The Dograh "reasoning delay" never includes hearing or voice time.
Options I put to the user (the order I recommended):
1. **Start speaking sooner:** Dograh buffers the reply until the first full sentence is ready (`TextAggregationMode.SENTENCE` in `dograh-flux-tts.py`, copied from Dograh's own Flux code, which uses SENTENCE because its function-tag filter needs whole sentences). Flux can take streamed tokens (`TextAggregationMode.TOKEN`). One-line experiment; may save a few hundred ms on every reply; check it does not speak function tags or sound choppy.
2. **Quick acknowledgement ("Mm-hm", "Right")** played the instant the caller stops, before the real answer; only on some turns or it sounds scripted. Needs a new processor in the call pipeline (more work).
3. **Faster model / go direct** (Anthropic direct instead of OpenRouter, or a faster model); needs another key and a quality check against the scenario test.
4. **Fewer round trips:** call `check_availability` and `find_appointment` together when moving a booking (saves about 2 s); remove or shrink the opening-to-main stage hop (one extra model turn at the start of each call; a true merge is unverified, the current build only hands off on the first stated need).
5. **Turn detection tuning:** shorter end-of-speech wait, Smart Turn analyzer setting (user already turned it on); trades speed for cut-offs.
**Small talk during a lookup** (the user's idea): a tool message cannot do it (it plays while the tool runs, which is a fraction of a second; a question would be talked over). It has to be a real two-turn conversation: the model says "Let me look that up for you. How's your day going?" and STOPS with no tool call, the caller answers, she reacts warmly, THEN she calls `check_availability` and reads the times. Prompt-only. Trade-offs I told the user: adds one back-and-forth to every booking, does not remove the model delay (it just happens while chatting), skip it for a caller who is stressed, has a leak or is in a hurry, limit to once per call and booking lookups only. Test it by ringing; text tests cannot judge it, and the scenario test's booking script assumes a straight availability answer so it will need adjusting.

## 3. The product plan and architecture (short; full version in `ARCHITECTURE.md`)

Goal: a multi-client platform. Each client gets a phone number, an AI receptionist trained on their business, calendar booking on their own calendar, message taking, transfer to a human (planned), and every call logged in a CRM workspace they can see.

Key decisions (numbered as in `ARCHITECTURE.md` section 1):
1. **Twenty stays out of the live call path.** The voice runtime and call-service answer calls without calling Twenty; Twenty is the system of record written to *after* the call. A CRM outage must never drop a call.
2. **Each entity has one system of record** (calls in Twenty; bookings in our Postgres/the client's calendar; tenants in our registry).
3. **Tenant registry** maps a dialed number to a client (tenant), their Twenty workspace, webhook token, booking hours, calendar.
4. **Twenty side is a Twenty App** (`twenty-app/`): a `Call` object plus an HTTP-route function `ingest-call` that verifies an HMAC signature over the raw body and upserts on `providerCallId`.
5. **Voice platform: Dograh leading, LiveKit Agents as fallback**, behind a `VoiceProvider` idea.
6. **Booking runs through HTTP tools on the call-service** behind a `Scheduler` interface: `LocalScheduler` (own slot rules) and `CalendarScheduler` (client's Google/Microsoft calendar).
7. **Licence**: Twenty is AGPLv3 with an "Application Exception": talking to it only via its API/webhooks keeps our service free to use any licence. Do not fork Twenty. Have a lawyer confirm before reselling.

Call flow today:

```
Caller's phone
  -> Voiso number (trial, UK London +44 20 3097 2037)
  -> Voiso inbound workflow "Dograh AI receptionist" (one Route step -> SIP URI)
  -> Dograh's Cloudonix SIP address  <uuid>.sip.cloudonix.net  (UDP/TCP 5060, TLS 443)
  -> Dograh agent (workflow 1: global prompt, "start call", "Main Agenda and Questions", "End Call")
        tools (HTTP, from inside the Codespace) -> call-service on localhost:3100
             /tools/availability  /tools/book  /tools/message  /tools/outcome
        call ends -> webhook node -> call-service /webhooks/dograh (bearer token)
                      -> outbox queue -> artifact copy (recording/transcript to private storage)
                      -> signed POST to Twenty  /s/ingest-call  -> Call record (upsert on providerCallId)
```

Entities / outcome codes: `BOOKED, MESSAGE_TAKEN, TRANSFERRED, TRANSFER_FAILED, INFO_GIVEN, CALLBACK_REQUESTED, OPTED_OUT, NO_OUTCOME`. Outcome precedence (decided in `server.ts`/`booking`): booking tool > opt-out found in the transcript (caller's lines only) > outcome the agent stated through `record_outcome` > message taken > platform disposition > extracted `outcome` variable.
